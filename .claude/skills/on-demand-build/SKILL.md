# On-demand build and release identity

A merge may intentionally produce no new build. Never bump automatically for every PR, push or merge. Confirm a new build with Chris before starting it; a clear explicit request for the same platform/source/build is confirmation, preserved across handoffs without a redundant question. Merge approval alone does not authorize a build. Resolve an unclear platform or source before mutation.

No current release/build identity has been established for this repository. Inspect its existing project and release configuration for the requested platform before selecting a counter. Do not import another project’s store assumptions, invent metadata or run a diagnostic build to discover a number. If no build mechanism is established, report that limit and leave identity unchanged.

For the confirmed action, pin the source and inspect the existing release mechanism and relevant live identity/history through authorized read access. Keep platform identities independent; leave an already usable identity unchanged, and change only what this build requires. Existing-artifact promotion creates no new build/counter. Missing trustworthy history blocks counter selection; report the exact missing observation. Preserve matching evidence and refresh mutable observations only when relevant intervening activity or staleness could cause a collision.

Keep build authorization separate from public release, deployment, unrelated merges, credential access and security/protection changes. Respect the active task’s budget; no unrequested diagnostic build, broad unit suite or paid job. Before any push or PR, inspect the exact branch/path triggers and external hosting/build integrations. Instructions do not change CI runtime or enforce another harness automatically.

For instruction-only push checks, use only an independently reviewed, explicitly installed local gate bound to the exact repository, base/head, approved Markdown paths, outgoing ref, trusted gate hashes and retained guarded Windows proof. An instruction or branch-provided classifier cannot approve itself. Version-only validation requires that repository’s already trusted format/classifier; otherwise retain normal code validation. Mixed instruction/version changes do not inherit a version-only shortcut. Never disable hooks/security checks or weaken protection. No tests or builds on the Mac; use the authorized shared Windows lane for focused behavioral qualification.

Return the confirmed scope, pinned source, relevant observed identity, exact changes or no-change reason, independent review and proof, and pending build/publication actions. This skill adds no hook, schedule, auto-build trigger or store write.
